Code Reusability

Inheritance & The super() Chain

Subclasses inherit attributes and methods from parents while adding specialized behaviors:

inheritance_demo.py
class Employee:
    def __init__(self, name: str, base_salary: float):
        self.name = name
        self.base_salary = base_salary

    def get_pay(self) -> float:
        return self.base_salary

# Derived Child Class (Subclass)
class SoftwareEngineer(Employee):
    def __init__(self, name: str, base_salary: float, bonus: float):
        # Delegate constructor to parent with super()
        super().__init__(name, base_salary)
        self.bonus = bonus

    # Method Overriding
    def get_pay(self) -> float:
        return self.base_salary + self.bonus

dev = SoftwareEngineer("Robiul", 80000, 15000)
print(f"Total Pay: ${dev.get_pay()}")  # 95000

Why super() is Essential:

super() dynamically resolves the parent class method according to Python's MRO. It eliminates hardcoding parent class names and safely supports multi-tier inheritance chains!

Interface Polymorphism

Polymorphism: Unified Interface, Dynamic Behavior

Different objects respond to the same method call with their own customized implementation:

polymorphism_demo.py
class Circle:
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r ** 2

class Square:
    def __init__(self, side): self.side = side
    def area(self): return self.side ** 2

# Polymorphic execution over a heterogeneous list
shapes = [Circle(5), Square(4), Circle(2)]

for shape in shapes:
    print(f"Shape Area: {shape.area():.2f}")

Duck Typing in Python:

"If it walks like a duck and quacks like a duck, it's a duck."
Python cares about what methods an object provides (behavior) rather than its strict inheritance ancestry!

Design Contracts

Abstract Base Classes (ABC)

Define strict API contracts that all child implementations must fulfill:

payment_contract.py
from abc import ABC, abstractmethod

# Abstract Class Contract (Cannot be instantiated directly!)
class PaymentGateway(ABC):
    @abstractmethod
    def process_payment(self, amount: float) -> bool:
        pass

# Concrete Implementation
class StripeProcessor(PaymentGateway):
    def process_payment(self, amount: float) -> bool:
        print(f"Processing ${amount} via Stripe API 💳")
        return True

gateway = StripeProcessor()
gateway.process_payment(150.0)

Why ABCs are Crucial:

If a child class forgets to implement process_payment(), Python immediately raises a TypeError: Can't instantiate abstract class at startup, preventing runtime crashes in production!

Magic Methods

Magic Dunder Methods (Operator Overloading)

Empower custom objects to interact naturally with Python's built-in operators (+, ==, len, print):

vector_math.py
class Vector2D:
    def __init__(self, x: int, y: int):
        self.x = x
        self.y = y

    # String representation for developers & print
    def __repr__(self):
        return f"Vector2D({self.x}, {self.y})"

    # Overload addition operator (+)
    def __add__(self, other):
        return Vector2D(self.x + other.x, self.y + other.y)

    # Overload equality operator (==)
    def __eq__(self, other):
        return self.x == other.x and self.y == other.y

v1 = Vector2D(2, 4)
v2 = Vector2D(3, 1)
print(v1 + v2)  # Vector2D(5, 5) 🎉

Essential Dunder Catalog:

  • __str__ / __repr__: String representation
  • __add__, __sub__, __mul__: Math arithmetic
  • __eq__, __lt__, __gt__: Logical comparisons
  • __len__, __getitem__: Container emulation
Pitfalls

4 Common Advanced OOP Traps ⚠️

Avoid these high-frequency object-oriented mistakes:

❌ 1. Instantiating Incomplete ABC

TypeError: Can't instantiate class with abstract methods!
Fix: Child MUST implement all @abstractmethods.

❌ 2. Forgetting super().__init__()

Child object missing parent attributes → AttributeError!
Fix: Always invoke super().__init__().

❌ 3. __str__ vs __repr__ Confusion

If __repr__ is defined, it serves as fallback for __str__.
Always define __repr__ first for debugging!

❌ 4. Overusing Inheritance

Deep inheritance trees create rigid brittle coupling.
Rule: Prefer Composition over Inheritance!

Mini-Project: Multi-Provider Payment Architecture

A modular payment architecture supporting Stripe, PayPal, and BKash with unified ABC contracts:

payment_engine.py
from abc import ABC, abstractmethod

class Gateway(ABC):
    @abstractmethod
    def pay(self, amount: float): pass

class BKashGateway(Gateway):
    def pay(self, amount: float):
        print(f"✅ Paid ৳{amount} via bKash (Instant OTP)")

class StripeGateway(Gateway):
    def pay(self, amount: float):
        print(f"✅ Paid ${amount} via Stripe (Credit Card)")

# Extensible Checkout (Never needs modification for new providers!)
def checkout(provider: Gateway, total: float):
    provider.pay(total)

checkout(BKashGateway(), 1250.0)

Open-Closed Principle (SOLID):

The system is Open for Extension (you can add ApplePay or PayPal tomorrow) but Closed for Modification (the checkout() function never needs to change!).
